# Litium Cloud CLI — Concepts

## Resource Hierarchy

```
Subscription
└── Environment (dev / staging / production)
    └── App (litium, litium-cdn, litium-insights, litium-storefront, ...)
        └── Resource (database, storage, redis, ...)
```

| Entity | Description |
|---|---|
| **Subscription** | A customer account / billing unit. Created by Litium. You get access via invitation. |
| **Environment** | A deployment target within a subscription. Typically one per lifecycle stage (dev, test, staging, prod). Each has a geographic location. |
| **App** | An installed application within an environment. Can be a public app (Litium Platform, CDN, Insights) or a private app (.NET web, Next.js web, etc.). |
| **Resource** | Infrastructure managed by an app (e.g. MS SQL database, file storage, Redis cache). |
| **Artifact** | A deployable package: compiled code, a database backup, or storage backup. Stored in the cloud and referenced during installation or deployment. |
| **Job** | An asynchronous operation (install, deploy, backup, etc.). Returns a job ID; track status with `litium-cloud status show --job <id>`. |
| **Location** | A geographic region where environments can be created. List with `litium-cloud location list`. |
| **Marketplace** | Catalog of available public apps. Use `litium-cloud marketplace list` to browse and `litium-cloud marketplace manifest` to download install YAML. |

## Artifacts

Artifacts are versioned, immutable packages stored in Litium Cloud storage. They are referenced by ID (e.g. `artifacts/d33ae52bb7044adb99d2b4df6fac6216`).

### Artifact types

| Type | Use case |
|---|---|
| `dotnet` | Compiled .NET web application (e.g. MVC Accelerator). Created from a `publish/` output folder. |
| `nextjs` | Next.js application (e.g. React Accelerator / Litium Storefront). Created from a `.next/` build. |
| `nodejs` | Generic Node.js application (no specific framework required). |
| `nuxtjs` | Nuxt.js application. |
| `sql-backup` | SQL Server `.bak` file for restoring a database during installation. |
| `storage-backup` | Zip archive of file storage (e.g. Media folder) for restoring during installation. |

Create artifacts with:
```bash
litium-cloud artifact create --file-path ./publish/ --artifact-type dotnet --subscription <id>
```

## YAML Manifests and `apply`

The `litium-cloud apply` command is the declarative way to install and configure apps. It reads a YAML manifest file describing the desired app state.

The canonical workflow:
1. **Download** a manifest template from the marketplace: `litium-cloud marketplace manifest --app <app-id> -f myapp.yaml`
2. **Edit** the manifest if needed (uncomment properties, add artifact references)
3. **Apply** the manifest: `litium-cloud apply -f myapp.yaml --subscription <id> --environment <id>`

Example manifest structure:
```yaml
# Generated by: litium-cloud marketplace manifest --app litium-platform
apiVersion: cloud.litium.com/v1
kind: App
metadata:
  name: litium
spec:
  app: litium-platform
  version: "latest"
  # properties:
  #   - name: artifact
  #     value: artifacts/<your-artifact-id>
  #   - name: sql_backup_file
  #     value: artifacts/<your-sql-backup-id>
  #   - name: storage_backup_file
  #     value: artifacts/<your-storage-backup-id>
```

## Context Management

Setting a context avoids repeating `--subscription` and `--environment` on every command.

```bash
# Set defaults for the current directory
litium-cloud context set --subscription <sub-id> --environment <env-id>

# Set globally (all directories)
litium-cloud context set --subscription <sub-id> --environment <env-id> --global

# Check current context
litium-cloud context show

# Clear context
litium-cloud context unset
```

The context is stored in a `.litiumcloud` file in the current directory (or `~/.litiumcloud` for global).

## Authentication

### Interactive (human users)

```bash
litium-cloud auth login
```

Opens a browser. Log in with a **Litium Account** (not your docs account). On first use, select "Sign up now". Tokens are cached in the OS keychain.

```bash
litium-cloud auth show      # who am I?
litium-cloud auth logout    # clear cached token
```

### Service principal (CI/CD)

Service principals authenticate with a certificate instead of a user account.

```bash
# 1. Create the service principal (outputs a PEM certificate file)
litium-cloud service-principal create --name "GitHub Actions" --expires 365 --file ./deploy.pem

# 2. Note the email address assigned to the service principal
litium-cloud service-principal list

# 3. Grant the service principal the permissions it needs (see Access Control)

# 4. Log in with the certificate
litium-cloud auth login --service-principal --username <sp-email> --certificate ./deploy.pem
```

The certificate must be unencrypted (no password). Supported formats: PEM, PFX.

## Access Control

Litium Cloud uses role-based access control with ACLs on each resource.

### Roles

Roles follow the pattern `<resource-type>/<level>`. Common ones:

| Role | Level | Description |
|---|---|---|
| `system/owner` | Highest | Full control over all resources (use sparingly) |
| `system/contributor` | High | Can create/modify resources |
| `system/reader` | Low | Read-only access |
| `subscription/reader` | Subscription | Can view subscription details (required for deploy) |
| `environment/reader` | Environment | Can view environment details (required for deploy) |
| `appresource/writer` | App | Can deploy artifacts to apps |
| `artifact/creator` | Artifact | Can create new artifacts |
| `artifact/reader` | Artifact | Can read/use existing artifacts |
| `apps/litium-platform/backup-operator` | App | Can create database/storage backups |

List all available roles: `litium-cloud role list`

### Adding access

```bash
# Add access to a subscription
litium-cloud subscription access-control add --email user@company.com --role system/reader --sub <sub-id>

# Add access to an environment
litium-cloud environment access-control add --email user@company.com --role environment/reader --sub <sub-id> --env <env-id>

# Add access to an app
litium-cloud app access-control add --email user@company.com --role appresource/writer --sub <sub-id> --env <env-id> --app <app-id>
```

### Groups

Groups make it easy to manage access for multiple users with the same role. Add a group email instead of individual emails in `access-control add`.

```bash
# Create a group
litium-cloud group create --name "DevTeam" --description "Development team"

# Add members
litium-cloud group member add --group <group-id> --email user@company.com

# Grant the group access to a resource
litium-cloud environment access-control add --email devteam@groups.company.com --role environment/reader --sub <sub-id> --env <env-id>
```

## Job Monitoring

Almost all cloud operations (install, deploy, backup) run as asynchronous jobs. After running such a command, a job ID is printed.

```bash
# Check job status
litium-cloud status show --job <job-id>

# View job logs
litium-cloud status log --job <job-id>
```

Jobs have these states: `Pending`, `Running`, `Succeeded`, `Failed`, `Cancelled`.

Use `--wait` on commands that support it to block until the job finishes:
```bash
litium-cloud app deploy --app litium --artifact <artifact-id> --wait
```
